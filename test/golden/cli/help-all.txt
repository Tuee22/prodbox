## prodbox aws teardown
prodbox aws teardown - Delete operational IAM user

Delete the operational IAM user. Default mode opens with a Pulumi-residue check and refuses if any AWS substrate stack (`aws-eks`, `aws-eks-subzone`, `aws-test`, `aws-ses`) still owns live resources. `--destroy-pulumi-residue` orchestrates `prodbox aws stack <stack> destroy --yes` (the `<stack>` CLI verb is `eks`/`aws-subzone`/`test`/`aws-ses`, not the registry name) in canonical order before deleting the operational IAM user; destroying the long-lived `aws-ses` stack triggers a 5-30 min SES re-verification and ~24h S3 bucket-name cooldown. `--allow-pulumi-residue` is the operator-acknowledged recovery escape hatch that bypasses the residue check entirely (stacks become orphaned). `--destroy-pulumi-residue` and `--allow-pulumi-residue` are mutually exclusive at parse time.
Options:
- --dry-run - Render the IAM teardown plan without mutating state
- --plan-file <PATH> - Write the rendered plan to a file
- --destroy-pulumi-residue - Run `prodbox aws stack <stack> destroy --yes` for each live Pulumi-managed AWS stack in canonical order before deleting the operational IAM user (mutually exclusive with --allow-pulumi-residue)
- --allow-pulumi-residue - Bypass the Pulumi-residue refuse-path that prevents deleting the operational IAM user while AWS substrate stacks still have live resources (operator-acknowledged recovery only; mutually exclusive with --destroy-pulumi-residue)

Examples:
- prodbox aws teardown  # Delete the operational IAM user (refuses if any AWS substrate stack is live).
- prodbox aws teardown --destroy-pulumi-residue  # Destroy live AWS substrate stacks in canonical order, then delete the operational IAM user.

## prodbox aws audit
prodbox aws audit - Inventory a stack's field in the provider

Ask the Provider, through the Lifecycle Authority, to take a read-only inventory of one stack's declared field in AWS: the stack's own resources, everything inside its VPC, the registered IAM names and the per-run volumes the cluster owns, with the retained state bucket as the positive control. The verdict is Clean, Residue or Unobservable and exits 0, 4 or 5; an unanswered query and a positive control that does not appear both exit 5. Raw identifiers go to standard output and nowhere durable. `--emit-readonly-script` prints the same reads as read-only AWS CLI commands for use when the Authority is unreachable and mutates nothing.
Options:
- --stack <STACK> - Stack to inventory: eks or test (both when omitted)
- --emit-readonly-script - Print the reads as a read-only AWS CLI script instead of taking the inventory

Examples:
- prodbox aws audit --stack eks  # Inventory the EKS stack's field in the provider.
- prodbox aws audit --emit-readonly-script  # Print the read-only reads for each stack.

Default mode is a PURE LOCAL UNINSTALL: it uninstalls RKE2 and preserves `.data/` (including the MinIO-backed per-run Pulumi state and the durable Vault PV) without querying, gating on, or destroying the per-run AWS Pulumi backend — so per-run AWS stacks (if any) are left untouched and remain destroyable afterward via `prodbox cluster delete --cascade` or `prodbox aws stack <name> destroy --yes`. With no RKE2 install present the default mode exits 0 having done nothing. `--cascade` orchestrates the full teardown (K8s drain + per-run Pulumi destroys + postflight tag sweep + cluster uninstall) as one atomic operator action; the K8s drain phase skips gracefully within a reachable run, but a cascade with no RKE2 install present reaches no phase at all and exits non-zero unless it asked AWS read-only on this invocation (it may prompt for a temporary admin credential) and the no-install conjunction held: an authored AWS coordinate, a clean sweep over every authored region, the credential tied to the deployment's account, and every retained root examined. Even then it reports no per-run residue in the swept regions, not an empty account, and it never reports a success it did not observe. The uninstall runs only on a confirmed-empty sweep: an unconfirmed or non-empty sweep leaves the local control plane running, because it is the only surface permitted to mutate AWS and destroying it would leave the answer with nothing able to act on it. No cascade exit authorizes deleting the retained root.
Options:
- --yes, -y - Confirm full cluster deletion
- --cascade - Orchestrate the full teardown (K8s drain + per-run Pulumi destroys + postflight tag sweep + cluster uninstall) as one atomic operator action
- --dry-run - Render the delete plan without mutating state
- --plan-file <PATH> - Write the rendered plan to a file

Examples:
- prodbox cluster delete --yes  # Uninstall the local cluster (pure local uninstall; leaves per-run AWS stacks untouched).
- prodbox cluster delete --yes --cascade  # Orchestrate the full teardown including per-run AWS destroys.
